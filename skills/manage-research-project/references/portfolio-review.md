# Prioritize a supplied research portfolio

Use this module for choices across named projects. It does not discover all
projects, establish a new project database or open every analysis directory.
Begin with the supplied project list, current summaries, milestone/blocker
evidence and this period's actual constraints.

## Establish comparable facts

For each included project, identify its goal, next deliverable, current phase,
known deadline, critical dependency, next feasible action and source age.
Distinguish delivery, exploration, infrastructure and collaboration needs.
Preserve unknown or conflicting fields; do not rank inaccessible projects as
failed or invent deadlines and staffing to make a complete table.

Read detailed results only if they could change a priority or reveal a
delivery-critical evidence gap. A current authoritative summary may suffice.
If portfolio records do not yet exist, answer from the supplied material and
state coverage rather than scaffolding or copying all project records.

## Make a feasible recommendation

Compare milestone value, confirmed deadlines, dependencies, available capacity
and opportunity cost against the user's stated objectives. Recommend a limited
set of actions that fits the known budget, and explain what is deferred and
what event would change that recommendation.

Keep total proposed effort within confirmed capacity when estimates exist.
Unknown effort is uncertainty, not zero; offer a bounded assessment or a
conditional plan instead of a false precise allocation. A blocked task should
not consume active execution capacity while its required input is unavailable,
although an authorized follow-up or independent preparation may be useful.

Do not make every project the top priority. Prefer reasoned priority tiers to
unjustified weighted scores. If a numerical model is requested, state weights,
uncertainty and sensitivity; the score is a decision aid, not an objective
measure of scientific value. Highlight at most three immediate actions unless
the user needs a fuller schedule.

Do not silently pause, cancel, change deadlines, promise collaborator work or
reposition a project. Distinguish recommendations from decisions covered by
existing authorization. Drafting an allocation does not start analyses, send
messages, create reminders or install scheduling infrastructure.

## Preserve one source for each project

Link priorities to the owning project/task IDs and source versions. Portfolio
summaries are projections of project facts, not independently editable copies
of task status. A portfolio-level allocation decision may own the allocation
itself without becoming the owner of every task it references.

For an authorized update, use [the document contract](document-contract.md)
and record the allocation in the existing appropriate decision location.
Update project records only for the changes actually authorized and supported;
do not run a checkpoint or audit in every project merely because it appears
in the review. An unavailable master remains unavailable even if a cache can
be read. Repeated or unchanged inputs should not produce duplicate tasks,
decisions or notifications.

## Output

Give the recommended order/allocation, a source-backed reason per priority,
the feasible next action, dependencies, and deferred work. State coverage and
uncertainty near any conclusion they limit. A compact comparison table is
usually sufficient; no mandatory dashboard, database or full review package.

Periodic review requires an actual user-requested scheduler and available
runtime. This module can be invoked manually; it does not continuously monitor
projects or guarantee notification, transaction or conflict-recovery behavior.
